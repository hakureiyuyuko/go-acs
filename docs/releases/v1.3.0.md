# v1.3.0 —— 概览页可选显示项 + 批量下发 WiFi 参数

两个都是「管十几台以上设备时才显得出来」的需求：**没有数据库结构变化**
（批量下发的结果复用现成的 `settings` 键值表）。

> 这一篇是这一轮迭代的**完整记录**：v1.3.1~v1.3.5 期间修的问题都并在这里了 ——
> 那些版本并没有真的发布过，拆成「修上一版」的六篇读起来是断的。

## 1. 概览页的列可以自己挑

**由来**：概览页固定列越加越宽（真机上十来列就得横向滚），但不同人盯的列又不一样 ——
排障的只看「最后上报」，装维只想看序列号和版本，FTTR 场景还想一眼看到收发光。

**做法**：新增「显示项」折叠面板，11 列可勾选 —— 状态 / 备注 / 序列号 / 软件版本 / 数据模型 /
最后上报 / 参数条数 / 上报 IP / 无线终端 / 收光 / 发光。
名称列与操作列不参与勾选（名称是进详情页的唯一入口，操作列是概览页唯一的下发动作）。

- 选择存在 **cookie `acs_cols`**（跨刷新保持，页面 5 秒自动刷新一次，存不住等于没做）；
- 同时也认 URL `?cols=status,serial`，**带 cols 参数时覆盖 cookie** —— 分享出去的链接
  在别人浏览器里也是同样的列；
- `cols=all` / `cols=default` 两个快捷值，界面上的「全选 / 恢复默认」就是它们；
- 没勾「收光 / 发光」时**不去查光功率**（列表页少一次查询）；
- 面板是 `<form method="get">`，**不依赖 JS** 也能用。

**默认列**：沿用原来的几列（状态 / 备注 / 序列号 / 软件版本 / 数据模型 / 最后上报 /
参数条数 / 无线终端）。新增的「上报 IP」「收光」「发光」三列**默认不勾** ——
这个特性的动机就是「列太宽要横向滚」，默认全勾反而更宽；而且「收光 / 发光」默认不勾
还顺带避免了每次打开概览页都跑一次光功率查询（见第 5 节）。

面板里每个列是同名的勾选框（`name="cols"`），浏览器提交上来是 `?cols=a&cols=b`
这种**多值参数**。最初用 `q.Get("cols")` 只取了第一个，勾几个都只渲染第一列；
现在用 `q["cols"]` 取全部再合并解析。

## 2. 批量下发 WiFi 参数

**由来**：一次改 50 台设备的 SSID，原来得点进 50 个详情页、每个频段各提交一次。

**做法**：概览页每行加复选框 + 全选，工具栏「批量下发 WiFi 参数」进 `GET /wifi/batch`：

- **目标设备**：页面自带设备勾选列表（URL `?ids=1,2,3` 预勾选，可现场增删），
  每台设备**标出在线 / 离线** —— 离线设备可以照旧勾选入队（下发完顺手唤醒一次），
  但得让人知道自己在给哪些离线设备排队；
- **频段范围**：全部频段 / 2.4G / 5G…，按**频段标签**选 —— 真机上 2.4G 是实例 1、5G 是实例 5，
  而且不同型号还不统一，按实例号选等于让使用者去背编号；
- **要改的字段**：字段表复用单设备页的 `wifiFieldDefs`，真正写哪个参数名在提交时
  **按每台设备的实报参数去解**（参数名、`xsi:type` 都用设备自己的），
  并显示「N / M 个频段支持」—— 有的设备没这个参数时不会默默少改几台；
- **只下发勾了的、且值真的变了的**：密码留空 = 不修改（批量场景最怕手滑清空几十台设备的密码）；
- 每台设备把各频段的改动**聚合成一条** `SetParameterValues`（不是每频段一条），
  下发完顺手唤醒一次；
- 结果存在 `settings` 表（`batch_wifi_last`），POST 后 303 回 `?run=1`：
  刷新后还在看，且每台设备的任务状态是每次展示时重新读的（几秒后就会从 pending 变 done）。

### 2.1 布尔项（启用 / 射频开关）是三态：不修改 / 启用 / 关闭

最初做成「改」和「值」两个并列的独立复选框，结果两处都出问题：

- 勾「改」+ 勾值 → 下发 `1`，而设备原值本来就是 `1`，被「值没变化」跳过，
  表现为「勾了、点了下发、什么都没发生」；
- 勾「改」+ 没勾值 → 服务端写 `0`（关闭），但前端又把这种提交拦下来弹窗，
  **等于批量只能开、关不掉**，和单设备页（取消勾选就写 `0`）不一致。

现在布尔项是一个 select 三选一，服务端据此决定「不改 / 写 1 / 写 0」。
布尔项**一律下发**（幂等写一次没有副作用），SSID / 信道这类仍然只在真变了才写。

## 3. 收光 / 发光

**数据口径**沿用 FTTR 区块「不编数字」的规矩：宁可显示 `-`，也不猜一个。

- 新增 `store.OpticalParams()`：一条 SQL 捞全库光功率参数（按名字粗筛），
  真正的判定复用 FTTR 那套 `opticalField()`（按叶子名认，且不会把无线的
  `TransmitPower` 当成发光功率）；
- 优先取**主机自己**的光功率；主机一个都没报但 FTTR 子设备报了，就取实例号最小的那台子设备，
  并在那一格 hover 上写明「来自子设备 N」—— 子光猫的收光和主机的收光不是一回事；
- 都没上报就显示 `-`（仓库里那两台真机确实不报，见 `docs/notes/implementation-notes.md`）。

### 3.1 光功率得先采才会出现

纳管时只下发基本信息（`DeviceInfo.*` 那批），没有任何入口会去取光功率，
所以这两列一开始全是 `-`。

- 新增 `FetchOptical`：枚举光口所在子树，枚举完同一会话接着取值；**不猜参数名**，设备报什么存什么；
- 设备页「光功率」区块 + 「重新采集光功率」按钮，REST 同款 `/api/devices/{id}/optical`；
- **首次纳管 / BOOTSTRAP 时自动采一次**（与自动采无线概况、WAN 概况同一处触发；
  光功率变化慢，不会每次 Inform 都采）。存量设备点一次设备页的按钮即可。

光口挂在哪棵子树上各家不一样，枚举范围：

| 数据模型 | 枚举的子树 |
| --- | --- |
| TR-098 | `WANDevice.` + `Optical.` |
| TR-181 | `Device.Optical.`（根未知时 TR-098/TR-181 四棵都试） |

> 华为 B671-1E3W 走 `WANDevice.1.WANPONInterfaceConfig.`，
> 中兴 ZXHN F610GV9 把光口放在 `InternetGatewayDevice.Optical.` 下 ——
> 只枚举 `WANDevice.` 会整个漏掉中兴。枚举代价很小（光口子树十来个参数），
> 漏一棵的代价是整台设备没读数。

### 3.2 参数名按语义认，不枚举

光功率在 TR-069 里没有统一命名（`RxPower` / `X_HW_RxPower` / `OpticalPowerRx` /
`ReceiveOpticalPower` / `PonRxPower`…），枚举名字永远列不全。
`opticalField()` 改成**按语义辨认**：

1. 叶子名（去掉 `_` / `-` / 空格后）必须含 `power` —— 不是功率就不谈光功率；
2. 还得有「光」的意味：含 `optical` / `pon`，或者是常见的 `rxpower` / `txpower` 写法；
3. 方向看 `rx` / `receive`（收）与 `tx` / `transmit`（发）。

特别注意：无线的发射功率叫 `TransmitPower`，**不是**光发射功率，
凡是 `transmitpower` 且不带 `optical` 的一律不算。

### 3.3 同一方向命中多个参数时，按语义选

一台猫上往往同时存在好几个带 `power` 的参数。以中兴 ZXHN F610GV9 为例，
`InternetGatewayDevice.Optical.Interface.1.` 底下同时有真读数和一堆私有字段
（百分比、原始 ADC 值、告警门限）。

最初是「遍历到第一个命中的就用」，而**遍历顺序取决于数据库返回顺序**，
不是参数的物理含义 —— 同一台设备刷新几次会显示不同的数
（实测显示成 `385 dBm / 16687 dBm`）。

现在给每个候选按参数名打一个「有多像标准光功率」的分，**分高者胜**：

- 名字含 `optical` / `pon` → +8；叶子名是 `RxPower` / `TxPower` / `OpticalRxPower` → +10；
  容器是 `WANPONInterfaceConfig` / `Optical.Interface` → +3
- 名字含 `threshold` / `alarm` / `percent` / `raw` / `status` / `voltage` … → **−10**

同分取更新时间更晚的（重采过的才是新的）；都一样则保留先到的（结果稳定，不来回跳）。

再叠一层**物理范围过滤**：光模块收 / 发功率真实范围约 **−40 ~ +10 dBm**，
超出的一律不当光功率显示 —— 宁可显示 `-`，也不显示 `385 dBm` 这种一眼假
但看着像真实读数的数。

### 3.4 读数统一两位小数

设备回的原值什么样都有：`-14`、`-14.0`、`-14.580`、`"-14 dBm"`、空。
统一格式化成两位小数（`-14.00 dBm`、`-23.40 dBm`）；
解析不出数字的（`N/A`、`--`）原样显示，**不会**当成 0 —— 那会看起来像一个真实读数。

### 3.5 能查到读数是哪个参数来的

- 概览页两列 hover 显示 `来源：<参数名>`；
- 设备页「光功率」区块列出「读数来源」；
- 设备页还有**光功率诊断**折叠面板（读不出光功率时默认展开）：列出这台设备所有
  疑似光功率的参数，每个标注是否被采用、落选原因（值不合理 / 分值输了 / 读数更旧 /
  主机优先），以及疑似私有单位时的换算建议（如 `385` → `÷100 ≈ 3.85 dBm`）。
  表格下面附一份纯文本版，方便直接复制出去排查。

  换算建议**只给提示、不自动套用** —— 猜单位等于编数。界面上也能区分
  「设备压根没报」和「报了但值不合常理被弃用」，这两种排查方向完全不同。

## 5. 光功率查询的开销

`store.OpticalParams()` 用的是 `WHERE lower(name) LIKE '%optical%' OR lower(name) LIKE '%power%'`
—— 函数包着列，用不上索引，只能全表扫。合成库实测（100 台 V271 规模、47 万行
`device_params`）约 **390 ms / 次**，对照走索引的 `WHERE device_id = ?` 约 5 ms。

叠上概览页 5 秒自动刷新和 `SetMaxOpenConns(1)` 的单连接，等于跟写入瓶颈抢那一条连接。
所以「收光 / 发光」两列**默认不勾**（勾了才显示、才查库）——
「没勾就别查」本来就是这段代码的意图，默认全勾会把它抵消掉。
