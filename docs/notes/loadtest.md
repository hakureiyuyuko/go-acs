# 压测：大规模断电恢复（设备集体上电）

场景：机房/小区整体断电恢复后，所有设备几乎同一瞬间发 `1 BOOT` 冲向 ACS。
要回答的问题是「ACS 的并发上限在哪、瓶颈是什么」。

跑法（脚本都是现成的）：

```bash
scripts/loadtest.sh                       # 阶梯 10/50/100/200/400
scripts/loadtest.sh -n 200                # 只跑一档
scripts/loadtest.sh -N "50 150" -e 4484   # 自定义阶梯与每台参数规模
scripts/loadtest.sh -E "ACS_DB_MAX_CONNS=4"   # 透传 ACS 环境变量（调优对照用）
```

每档都用**全新的库和实例**（所有设备都是新设备 = 最坏情况），产物落在
`~/Desktop/TEMP/loadtest/<时间戳>/`：`summary.txt` + 每档的 `acs.log` / `sim.log`。

## 设备模板：照真机华为 V271-20

| 项 | 值 |
|---|---|
| 数据模型 | TR-098（`InternetGatewayDevice.`）|
| FTTR 子设备 | 3 台，光纤组网（带光功率参数）|
| `X_HW_APDevice` 子树 | **4484 个参数**（真机实测就是这个量级）|
| 每台参数总量 | ≈ 4700 个（ACS 纳管时会枚举 + 取值 + 全部落库）|
| 上报方式 | 单进程 `-count N` 模拟 N 台，全部同时发 `1 BOOT`，事件后退出 |

## 结论

1. **并发会话本身不是问题**：200 台设备同时建会话、同时领任务，小参数时 10.3 秒全部干净完成
   （200/200、0 错误）。ACS 没有并发上限、不拒绝新会话，也不需要排队。
2. **瓶颈是「每台设备的参数写入量」**：4 核机器上 ACS 全程只用 **1.05–1.14 个核**，
   吞吐卡在 **约 1.6–1.8 万参数行/秒**（≈ **3.5–4 台 V271 规模设备/秒**）。
   原因就是 `SetMaxOpenConns(1)`：一个连接把所有读写串行化，多核用不上。
3. **30 秒口径**（CPE 常见的 HTTP 超时）：**≤100 台可干净完成**（100 台 26s）；
   200 台约 60s、400 台约 2 分钟 —— 超时的设备**数据其实已经全量入库**
   （940,600 / 1,835,064 行 = 每台 4702），只是会话要在它下一次周期上报时收尾。
   现场表现就是「恢复供电后一两分钟内设备陆续都上来了」，不需要人工干预。
4. **不要靠调大连接池来提速**：1 → 4/8 连接虽然把 200 台从 59s 拉到 25s / 17.7s，
   但出现 195–196 条 `database is locked (SQLITE_BUSY)`，参数只入库 44% / 32%，任务领取也失败。
   `busy_timeout(5000)` 挡不住这种长事务冲突（一批就是几千行的 upsert）。
   **`SetMaxOpenConns(1)` 是正确性要求，不是保守做法** —— 所以这个口子没有做成配置项。
5. 想再往上提速，得改写入路径本身（都还没做）：
   - 批量多行 `INSERT ... ON CONFLICT` 代替逐行 upsert，减少语句数与 prepare 开销；
   - 复用 prepared statement（现在每个事务里都 Prepare 一次）；
   - 「单写线程 + 队列批量提交」，让写库变成顺序大事务；
   - 少写点：`X_HW_APDevice` 下 4484 个参数是否都要落库（界面只用到其中一部分），
     或者对稳定子树改成「变化才写」。
6. 压力测试自身的两个坑（值得记，第一次踩到差点拿到假数据）：
   - 同一进程里模拟 N 台设备时，它们默认共用 `127.0.0.1` 和同一个 User-Agent，
     而 ACS 的会话兜底指纹是 `来源 IP + UA + 账号` → **N 台设备被当成同一个会话**，
     任务串到别的设备上、大部分直接被 204 结束。现在每台设备绑一个 `127.0.0.0/8` 里的独立源 IP
     （真机各有各的管理 IP，这才是真实形态）。
   - 真机（和规范）会回传 session cookie，模拟器原来没做 → 也补上了。
     两个都修完，压出来的数字才和现场对得上。

## 现场建议

- 一般规模（几十台到一百多台）**不需要任何调优**：断电恢复后设备会在各自周期内陆续上报完，
  人不用管。
- 几百台同时恢复时，关注的是「多久全部上来」而不是报错：实测 400 台约 2 分钟数据全量入库，
  只不过部分设备的单次会话会超时、留到下一次周期补完。想更快就得改写入路径（见上）。
